# Voice Intent Normalizer 设计规格

日期：2026-07-29  
状态：待用户书面审阅  
建议技能名：`voice-intent-normalizer`

## 1. 背景

用户经常通过中文语音转文字向 AI 发布指令。通用语音识别对以下内容容易产生错误：

- 中文同音字和近音词，例如把“会话”识别为“绘画”。
- 英文产品名、模型名和工具名，例如把 `Codex` 识别为 `code X`。
- 行业术语、项目内部名称、人物名和品牌名。
- 快速进入中文语境的新兴 AI 词汇。
- 用户长期形成的个人表达偏好和常用对象。

本项目不接管麦克风或实时语音识别，而是在语音已经转换为文字并提交给 Agent 后，结合词库、项目内容、当前对话和个人记忆，推断用户真实意图。它修正 Agent 的理解，不修改已经发送的原消息。

## 2. 产品目标

### 2.1 核心目标

1. 用户安装一次后，在不同 Codex 会话和项目中自动生效，不要求逐次手动调用技能。
2. 对中文语音转写产生的同音字、近音词、英文音译和专业术语错误生成可靠候选。
3. 根据当前行业、当前项目、当前对话和个人偏好选择最合理的候选。
4. 高置信度错误静默纠正；关键歧义必须询问用户。
5. 从用户明确纠正和重复使用中积累可查看、可删除、可导出的个人词库。
6. 通过独立热点词库持续吸收新模型、新产品、新工具和新概念，不要求重新安装整个技能。
7. 默认在本地处理个人词库和项目词库，不上传私有内容。

### 2.2 非目标

- 不替换或改造 Codex、ChatGPT、微信等应用自带的语音按钮。
- 不在说话过程中提供逐字实时转写。
- 不修改聊天记录中已经发送的用户原文。
- 不承诺读取所有原始历史会话。
- 不让模型仅凭一次猜测永久学习新映射。
- 不把项目术语、个人偏好或对话内容上传到公共热点词库。
- 不宣称发明了热词增强、上下文语音识别或专业词典技术。

## 3. 适用范围

第一版以本地 Codex 桌面端、CLI 和 IDE 扩展为主要运行环境。技能采用标准 `SKILL.md` 结构，尽量保持对其他支持 Agent Skills 的工具可移植。

需要文件系统写权限的能力包括：

- 安装全局启动规则。
- 保存个人词库和本地热点词库缓存。
- 在当前项目生成项目词库缓存。
- 写入用户明确确认的纠错映射。

在不允许文件写入的环境中，技能仍可基于内置词库、当前对话和当前可读项目内容执行一次性纠错，但不能持久学习。

## 4. 总体架构

系统由四个主要模块组成：

1. **启动配置器**：完成一次性安装、自动触发配置、严格模式 Hook 配置和卸载。
2. **分层词库系统**：管理基础、热点、行业、项目和个人五类词库。
3. **纠错引擎**：生成候选、评分、执行语义保护并作出纠错决策。
4. **学习与反馈模块**：管理候选、重复和确认状态，以及负向规则。

### 4.1 数据流

```text
用户提交文字
  → 全局轻量规则判断是否疑似语音转写
  → 隐式调用 voice-intent-normalizer
  → 加载适用词库
  → 检测异常片段
  → 生成同音、近音、英文音译和术语候选
  → 结合项目、对话、领域和个人偏好排序
  → 应用安全边界
  → 静默按纠正意图执行 / 询问用户 / 保留原文
  → 在满足学习条件时更新本地状态
```

## 5. 自动触发设计

### 5.1 标准模式

安装器向 `~/.codex/AGENTS.md` 添加一个带开始和结束标记的短配置段。配置段要求 Agent：

- 把中文用户输入视为可能包含语音转写错误。
- 在执行前进行轻量检查。
- 出现同音、近音、英文音译、专业术语或语义断裂迹象时，隐式调用本技能。
- 高置信度错误可静默纠正。
- 会改变任务结果的歧义必须询问用户。
- 用户使用“我说的是……”等明确纠正结构时，把映射交给学习模块。

安装器不得覆盖用户已有 `AGENTS.md`，重复执行必须保持幂等。

### 5.2 严格模式

严格模式额外安装 `UserPromptSubmit` Hook。Hook 在每条用户提示提交时运行轻量检测，并只向 Agent 注入是否需要执行完整纠错的附加上下文。

严格模式是可选项，不作为默认设置，原因包括：

- 配置复杂度更高。
- 每条提示都会运行检测脚本。
- 不同 Agent Skills 宿主对 Hook 的支持不一致。

### 5.3 典型触发信号

- 中文句子语义断裂，但存在明显同音替代。
- 中英文混合片段出现异常空格、大小写或音译。
- 当前项目中存在与错误片段发音相似的准确名称。
- 输入包含“我说的是”“不是 X，是 Y”等自我纠正。
- 片段命中行业、热点或个人词库的已知别名。
- 输入包含大量专有名词或疑似语音填充词。

仅出现普通错别字且不影响理解时，不必加载完整技能。

## 6. 分层词库

所有词库共享同一词目结构和匹配引擎，通过 `scope`、来源和权重区分作用域。

### 6.1 基础词库

基础词库随技能发布，包含稳定、跨行业的常见 AI 和软件术语，以及高频中文语音识别错误。

特征：

- 离线可用。
- 随技能版本更新。
- 更新频率低。
- 不包含用户或项目私有信息。

### 6.2 热点词库

热点词库包含快速进入中文语境的新模型、新产品、新工具、新概念、热门项目和高频英文缩写。

特征：

- 与技能逻辑独立版本化。
- 默认每天首次使用时检查一次更新。
- 只下载公开 JSON/JSONL 数据，不执行远程代码。
- 下载失败时继续使用上一个有效版本。
- 支持自动更新、手动更新、关闭更新和固定版本。

### 6.3 行业词库

行业词库按领域组织，例如：

- AI 与大模型
- 软件开发
- 产品设计
- 视频制作
- 金融
- 法律
- 医疗
- 电商和新媒体

技能根据当前项目文件、对话和用户显式选择激活一个或多个行业包。行业词库可以由社区独立贡献。

### 6.4 项目词库

项目词库只对当前文件夹或代码仓库生效。内容包括：

- 产品和客户名称。
- 文件名、目录名、模块名。
- 类名、函数名、组件名和 API 名称。
- 项目文档中的高频术语和缩写。
- 用户在当前项目内确认的专有映射。

项目词库是可重新生成的本地缓存，不自动提升为个人词库。不同项目之间不得互相泄露项目词目。

### 6.5 个人词库

个人词库跨项目生效。内容包括：

- 用户喜欢或经常提及的博主、作者、品牌和人物。
- 用户偏好的表达方式和中英文写法。
- 用户明确确认过的通用纠错映射。
- 跨会话重复出现且具有稳定意义的个人术语。
- 用户设置的禁止纠正规则。

个人词库只保存在本地，默认不提交到 Git，不参与公共热点词库更新。

### 6.6 词目格式

运行时词库使用 JSONL，每行一个词目，以便标准库解析、增量更新和社区审核。示例：

```json
{"canonical":"Codex","scope":"hot","aliases":["code X","code ex"],"phonetics":["kou-de-ke-si"],"domains":["ai","software-development"],"weight":0.9,"status":"curated"}
```

项目和个人词目可以增加来源信息：

```json
{"canonical":"WorkBuddy","scope":"project","project_id":"project-a","aliases":["Work body"],"weight":1.0,"status":"confirmed","source":"project-symbol"}
```

必需字段：

- `canonical`
- `scope`
- `aliases`
- `domains`
- `weight`
- `status`

可选字段：

- `phonetics`
- `project_id`
- `source`
- `first_seen`
- `last_seen`
- `use_count`
- `negative_aliases`
- `notes`

## 7. 项目词库生成

项目扫描器从以下公开项目表面抽取候选：

- 文件和目录名称。
- Markdown 标题和高频加粗术语。
- 代码中的公开符号、类名、函数名、类型名和枚举名。
- 包名、依赖名和产品配置中的非敏感标识。
- README、设计文档和用户指定的术语文件。

默认忽略：

- `.git/`
- `node_modules/`
- `vendor/`
- 构建产物和缓存目录
- 二进制文件
- `.env`
- 密钥、令牌和凭据文件
- 用户配置的排除路径

扫描器只保存候选词和必要的来源位置，不复制大段项目内容。项目词库生成失败时，纠错引擎继续使用其余词库。

## 8. 候选生成与评分

### 8.1 候选来源

- 已确认别名的精确匹配。
- 无声调拼音匹配。
- 常见前后鼻音、平翘舌和轻声近音规则。
- 英文拆词、连读、字母读音和中文音译别名。
- 字符编辑距离。
- 当前项目准确标识符。
- 当前对话中的高频实体。
- Codex Memories 提供的个人偏好线索。
- 大模型基于整句语义生成的补充候选。

确定性脚本负责产生和排序可解释候选；大模型只负责补充语义判断，不得绕过安全边界。

### 8.2 评分因素

概念评分由以下因素组成：

```text
总分
= 发音相似度
+ 文本相似度
+ 当前领域匹配度
+ 当前项目匹配度
+ 当前对话匹配度
+ 个人使用频率
+ 用户确认权重
- 负向规则惩罚
- 歧义惩罚
```

实现阶段通过测试语料校准具体权重。用户确认映射和项目精确标识符拥有最高证据等级，但仍需经过危险内容保护。

### 8.3 决策等级

#### 高置信度

满足以下条件之一且无安全冲突时，可静默按纠正后的意图执行：

- 命中用户明确确认的映射。
- 命中当前项目准确名称，且发音高度相似。
- 候选与当前对话语义明显一致，领先第二候选的分差达到校准阈值。
- 英文错误转写命中热点或行业词库，且当前领域明确吻合。

#### 中置信度

候选合理但存在另一个接近解释时：

- 如果不同解释不会改变任务结果，可保留原文并继续。
- 如果不同解释会改变文件、功能或操作目标，必须询问用户。

#### 低置信度

不自动修改。按原文理解，或按正常任务澄清规则询问用户。

## 9. 安全边界

以下内容必须使用更严格的确认条件：

- 文件路径和目录路径。
- 命令行参数。
- 数据库、表、字段和环境名称。
- API 名称、代码符号和版本号。
- 金额、日期、百分比和其他数字。
- 删除、覆盖、发布、部署、提交、推送和权限变更等重要操作。

只有命中项目中的准确对象，或用户已经明确确认过映射时，才能自动替换这些内容。否则必须询问用户。

技能不得为了让句子更通顺而改变用户的任务范围、语气立场或事实主张。

## 10. 学习与反馈

### 10.1 学习状态

- `candidate`：只出现过或由模型推断，当前会话可用，不永久确认。
- `repeated`：跨会话多次出现，提高候选权重，但仍不是确定事实。
- `confirmed`：用户明确纠正或主动确认，可写入个人或项目词库。
- `rejected`：用户明确否定，写入负向规则，避免重复纠正。

### 10.2 明确纠正模式

以下结构视为强学习信号：

- “我说的是 X。”
- “不是 A，是 B。”
- “以后把 A 理解成 B。”
- “不要再把 A 改成 B。”

写入前必须判断作用域：

- 只属于当前仓库的名称进入项目词库。
- 跨项目的个人偏好或通用名称进入个人词库。
- 无法判断时默认进入当前项目词库，或在影响较大时询问用户。

### 10.3 用户控制

技能必须支持以下自然语言操作：

- 查看最近学到的词。
- 查看某个词的来源和匹配别名。
- 确认或拒绝候选词。
- 删除个人词目或项目词目。
- 禁止某个自动替换。
- 导入和导出个人词库。
- 清除指定项目的生成缓存。

### 10.4 Codex Memories

Codex Memories 用于提供宽泛的个人偏好和跨会话线索，不作为精确纠错映射的唯一来源。已确认词目必须写入技能自己的可审计词库。

## 11. 热点词库更新

### 11.1 更新流程

```text
当天首次触发技能
  → 读取 last-update.json
  → 超过 24 小时则获取远程 manifest
  → 比较词库版本
  → 下载新的数据文件
  → 校验 SHA-256 和 JSONL 结构
  → 写入临时文件
  → 验证通过后原子替换当前版本
  → 记录更新时间和版本
```

### 11.2 本地路径

建议使用：

```text
~/.codex/voice-intent/
├── personal.jsonl
├── preferences.json
├── hotwords/
│   ├── manifest.json
│   ├── zh-ai.jsonl
│   └── last-update.json
└── projects/
    └── <project-id>/
        ├── project.jsonl
        └── scan-state.json
```

### 11.3 安全要求

- 只接受受支持版本的清单和数据格式。
- 只下载允许的 GitHub Release 或固定官方域名。
- 验证 SHA-256。
- 拒绝包含脚本、路径穿越或未知字段类型的数据包。
- 先写临时文件，验证后原子替换。
- 保留最后一个有效版本以便回退。
- 网络失败、清单损坏或校验失败不得阻塞用户任务。
- 不上传任何个人、项目或对话数据。

### 11.4 更新边界

热点词库数据升级不要求重新安装技能。以下变化要求升级技能版本：

- 匹配算法变化。
- 数据格式发生不兼容变化。
- 安装器或 Hook 行为变化。
- 新增依赖或权限。
- 安全策略发生变化。

## 12. 安装、升级与卸载

### 12.1 安装

安装器：

1. 检查目标技能目录。
2. 安装技能文件。
3. 创建本地状态目录。
4. 向全局 `AGENTS.md` 追加带唯一标记的配置段。
5. 根据用户选择安装标准模式或严格模式。
6. 验证技能可被发现。
7. 运行一组本地冒烟测试。

### 12.2 升级

- 保留个人词库、负向规则和项目缓存。
- 迁移旧数据前创建备份。
- 数据迁移失败时回退技能版本并保留原数据。
- 不覆盖用户手动编辑的全局规则，只更新本技能标记范围内的内容。

### 12.3 卸载

- 删除技能目录。
- 只删除 `AGENTS.md` 中本技能的标记配置段。
- 只删除本技能安装的 Hook。
- 默认保留个人词库并询问是否一并清除。
- 不修改其他技能、Hooks 或用户配置。

## 13. 错误处理

| 错误 | 行为 |
|---|---|
| 未安装拼音依赖 | 使用显式别名、文本和语义匹配，并提示完整能力不可用 |
| 项目扫描失败 | 使用基础、热点、行业和个人词库继续 |
| 热点更新超时 | 使用当前本地版本继续 |
| 热点文件校验失败 | 拒绝新文件并回退上一个有效版本 |
| 个人词库损坏 | 隔离损坏文件，使用最近备份并报告 |
| 没有写权限 | 以只读模式运行，不保存学习结果 |
| 候选分数接近 | 不静默纠正影响任务结果的片段 |
| 用户否定纠正 | 立即恢复原意并记录负向候选 |

## 14. 技术选择

第一版脚本使用 Python 3.10+：

- 标准库处理 JSONL、哈希、网络下载、缓存和原子文件替换。
- `pypinyin` 作为完整中文拼音匹配的可选依赖。
- 缺少 `pypinyin` 时仍保留显式别名、文本相似度和模型语义判断。
- 不引入数据库；个人和项目词库均为可读、可审计的文本文件。
- 不在运行时静默安装依赖。

技能主体保持简洁，把详细词库规范、贡献规范和测试语料说明放入按需加载的 references。

## 16. 测试设计

### 16.1 单元测试

- JSONL 词目解析和校验。
- 拼音归一化和近音规则。
- 英文拆词、字母读音和音译别名。
- 作用域过滤。
- 候选排序和负向规则。
- 更新清单、SHA-256 和回退。
- `AGENTS.md` 标记段的幂等安装与卸载。

### 16.2 语料测试

测试集至少覆盖：

- 中文同音字和近音词。
- 英文产品名的中文音译。
- 中英文混合输入。
- 项目专有名词。
- 用户自我纠正。
- 多个合理候选。
- 正常文本不应被修改。
- 文件路径、命令、数字和重要操作。

### 16.3 状态测试

- `candidate → repeated → confirmed`。
- 用户拒绝后生成负向规则。
- 个人词库跨项目生效。
- 项目词库不跨项目泄露。
- 无写权限和只读模式下不持久写入。
- 重复安装、升级和卸载不破坏用户文件。

### 16.4 故障测试

- 断网。
- 远程清单损坏。
- 热点词库哈希错误。
- 本地词库部分损坏。
- 无写权限。
- 缺少拼音依赖。
- 项目体积过大或包含大量二进制文件。

## 17. 验收标准

第一版必须满足：

1. 已知词库错误的候选召回率不低于 95%。
2. 普通正确文本的错误自动修改率低于 2%。
3. 关键歧义不得静默选择错误答案。
4. 项目词库不得跨项目自动生效。
5. 用户明确纠正可以持久保存并在新会话中复用。
6. 每天最多自动检查一次热点词库更新。
7. 热点更新失败时继续使用上一个有效版本。
8. 安装、重复安装、升级和卸载不得破坏用户已有 `AGENTS.md`。
9. 默认不上传项目、对话或个人词库数据。
10. 在缺少网络和可选拼音依赖时，技能仍能降级运行。

## 18. 开源定位

项目定位为：

> 面向中文语音转写指令的、项目感知且可持续学习的 Agent Skill。

差异化重点：

- 不绑定某个语音识别引擎。
- 自动扫描当前项目生成词目。
- 同时使用行业、热点、项目和个人上下文。
- 通过全局规则实现跨会话无感触发。
- 采用可审计、可扩展的开放词库格式。
- 明确区分候选、重复、确认和拒绝，降低错误学习风险。

建议使用 Apache-2.0 许可证。公共词库贡献必须注明来源，不接受直接复制受限制的商业词典。

## 19. 实施阶段划分

实施计划应按以下顺序展开：

1. 技能骨架和词目数据规范。
2. 确定性候选生成与单元测试。
3. 分层词库加载和作用域隔离。
4. 项目扫描器。
5. 个人学习与负向规则。
6. 热点词库更新和回退。
7. 安装、严格模式 Hook 和卸载。
8. 端到端语料验证与文档收敛。

只有在本设计规格得到用户书面审阅确认后，才进入详细实施计划和代码开发。
